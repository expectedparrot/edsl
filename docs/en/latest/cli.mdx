The EDSL command-line interface lets you create and validate study objects, run surveys with language models, publish surveys for human participants, and inspect or export responses. Use it from a terminal, a script, or a coding agent.

This guide uses `ep`. The commands `edsl` and `python -m edsl` are equivalent entry points. An EDSL `Agent` describes a survey respondent; a coding agent is software that can use the CLI to build and run a study.

## Install and discover commands

Install EDSL in your Python environment:

```bash
pip install edsl
```

Check the installed version and available commands:

```bash
ep --help
ep info
ep run --help
ep jobs --help
ep results --help
ep schema list
ep state --help
ep orchestration --help
ep skills list
```

Use the installed CLI's help to check flags before constructing a command. `ep info` reports configuration diagnostics and redacts credentials. See [Installation](/en/latest/installation) for environment setup.

For shared-state machines, `ep state validate`, `ep state inspect`, and
`ep state simulate` work with serialized Machine JSON. After a run, use
`ep results state --file results.ep` to inspect persisted state bindings and
snapshots. See [Testing and serialization](/en/latest/shared-state/testing-and-serialization#using-the-ep-cli)
for the input format and examples.

The installed EDSL distribution also includes version-matched skill bundles.
Use `ep skills list --routing` to see their routing descriptions and available
references, `ep skills search <query>` to find guidance, and `ep skills show
<name>` to retrieve a skill with its linked references. Use
`ep skills install --target <path>` to copy the bundles into a harness's skill
directory. The bundled `edsl-shared-state` and `edsl-orchestration` skills
describe the two features below.

`ep workflow` manages research-task gates. Portable respondent workflows have a
separate namespace: `ep orchestration validate`, `inspect`, and `run` operate on
`WorkflowExperiment` JSON files. `run` writes its durable database and state
files to an output directory; configured LLM executors can make model calls.
Use `--responses` to replay supplied answers without model calls, and `--resume`
to continue an existing run. See [Workflow CLI commands](/en/latest/workflows#cli-commands).

## Try a local example

Run these commands in a working directory where you want to save the example files. They create a survey and execute it with EDSL's test model, which returns a fixed answer. This example requires no model credentials and makes no paid model calls; its output is test data.

Create a question and save it as a survey:

```bash
ep surveys create \
  --question-type free_text \
  --question-name feedback \
  --question-text "What would improve this service?" \
  --output survey.ep
```

Create the test model configuration and combine it with the survey in a saved job:

```bash
ep models create \
  --model test \
  --canned-response "A test response." \
  --output test-models.ep

ep jobs build \
  --survey survey.ep \
  --models test-models.ep \
  --output test-job.ep
```

Validate the job, run it locally, and inspect the answer:

```bash
ep validate --file test-job.ep
ep run test-job.ep --local --output test-results.ep
ep results select --file test-results.ep --column answer.feedback --limit 5
```

The selected answer is `A test response.` The completed responses are saved in `test-results.ep`; the `run` command returns execution metadata rather than response rows.

Read each command's JSON response and check `status` before proceeding to the next command.

## Read command responses

By default, operational commands write one JSON document to stdout. Diagnostics go to stderr, and output captured from lower-level operations may appear in `warnings`. Help output from `--help` is plain text. Options that explicitly request raw output, such as `--output -` on object-creation commands, bypass the usual response envelope.

A successful response has this structure:

```json
{
  "status": "ok",
  "data": {},
  "warnings": []
}
```

`data` contains command-specific information. When a command saves a file, inspect the returned save metadata for its path and format.

An error response has this structure; `suggestion` is included when available:

```json
{
  "status": "error",
  "error": {
    "code": "USAGE_ERROR",
    "message": "Completed run results must be written to a file.",
    "suggestion": "Use --output results.ep or --output results.json."
  }
}
```

For automation, parse stdout as JSON, inspect `status`, read warnings, and check the process exit code. Do not extract identifiers or URLs from progress messages. For example:

```python
import json
import subprocess
import sys

process = subprocess.run(
    ["ep", "info"],
    capture_output=True,
    text=True,
)
response = json.loads(process.stdout)

for warning in response.get("warnings", []):
    print(warning, file=sys.stderr)

if response["status"] == "error":
    error = response["error"]
    raise RuntimeError(
        f"{error['code']}: {error['message']} "
        f"{error.get('suggestion', '')}"
    )

process.check_returncode()
data = response["data"]
```

If stdout cannot be parsed as JSON, treat it as a command failure and inspect stderr. Do not continue with missing or guessed output values.

## Create and validate study objects

Prefer `.ep` packages for objects you want to save, inspect, reuse, or share. The CLI also accepts serialized JSON for many commands. A `Jobs` object combines the survey with its agents, scenarios, and models.

Inspect schemas before constructing serialized objects by hand:

```bash
ep schema show --class Survey
ep schema show --class Jobs
ep schema show --question_type multiple_choice
```

You can also use object-creation commands directly. For example, add a question to the survey from the local example:

```bash
ep surveys add-question survey.ep \
  --question-type multiple_choice \
  --question-name recommend \
  --question-text "Would you recommend this service?" \
  --option Yes \
  --option No

ep validate --file survey.ep
ep inspect survey.ep
```

`add-question` updates the survey package in place. A job built earlier retains its saved survey, so rebuild the job to include the new question. Use `ep agents create --help` and `ep scenarios create --help` for creating respondent profiles and scenario data from files.

To read a survey in the terminal, print its Markdown questionnaire or save it for review:

```bash
ep surveys show survey.ep --markdown
ep surveys show survey.ep --markdown --with-question-names --with-question-types > questionnaire.md
```

Use either heading flag independently. With both flags, a heading reads
`3. [age] “What is your age?” (numerical)`. By default it reads `3. “What is your age?”`.
Dropdowns show the first five choices and a count of the remaining choices. Add
`--expand-options` to list them all. This flag only changes the preview. The
dropdown's `top_k` determines how many matches a search returns.

Budget questions show an allocation table with the total above it. Demand questions
pair each price with an empty quantity cell. Rank questions show the available
choices followed by the requested number of blank ranking positions.
Group discussions list their stages in order. Active survey instructions appear before
each question they apply to, including when you open that question on a later page.
Matrix questions display items as rows and response options as columns. Questions appear
in authored order with response options and routing. Jinja expressions and control
tags in question text appear as inline code, so you can see where answers or scenario
values will be inserted and which wording is conditional.
For example, a Yes/No question can display `○ No → Go to question 3`. The skipped question also shows its skip
condition above the answer choices, even on a page by itself. More complex
conditions appear at the question where they are evaluated. The flag writes Markdown
directly to stdout on success. Omit it for the normal JSON summary.

Set answer-option randomization on a survey with `set-option-randomization`. Repeat `--question` for each question; use `--pin-options` with a JSON object or a path to one when some options should stay in their original positions. This works for static choices and whole option lists resolved from scenarios or prior answers:

```bash
ep surveys set-option-randomization survey.ep \
  --question recommend \
  --pin-options '{"recommend":["No"]}'
ep surveys show survey.ep
ep validate --file survey.ep
```

Use `--clear` to remove the survey's option-randomization settings. See [Surveys](/en/latest/surveys#randomize-answer-option-order) for execution behavior and Python examples.

For model-run studies, configure forward/reverse presentation of linear scales
with `ep surveys set-scale-direction-randomization`. Repeat `--question` for
each scale; use `--clear` to remove the policy:

```bash
ep surveys set-scale-direction-randomization survey.ep --question satisfaction
ep surveys show survey.ep
ep surveys set-scale-direction-randomization survey.ep --clear
```

### Assign treatment conditions


Use an explicit schedule to assign each respondent/model/iteration unit to one scenario condition. Condition values are scenario indices in the Jobs package. Save a policy JSON file with `conditions`, `schedule`, `unit`, and optionally `unit_id_field`, `exposure_questions`, `balance`, and `planned_iterations`:

```json
{
  "version": 1,
  "conditions": {"control": 0, "treatment": 1},
  "schedule": {"agent:r1": "control", "agent:r2": "treatment"},
  "unit": "agent",
  "unit_id_field": "respondent_id",
  "exposure_questions": ["outcome"],
  "balance": "exact",
  "planned_iterations": 1
}
```

Apply and validate the policy, then inspect realized assignment and exposure in results:

```bash
ep jobs set-treatment-assignment jobs.ep --policy treatment-policy.json
ep validate --file jobs.ep
ep run jobs.ep --local --output results.ep
ep results select --file results.ep \
  --column randomization.treatment_assignment.condition \
  --column randomization.treatment_assignment.assignment_id \
  --column randomization.treatment_exposure.exposed
```

Unit keys start with `agent:<id>`; `agent_model` appends `|model:<index>`, `agent_iteration` appends `|iteration:<index>`, and `agent_model_iteration` appends both. `balance: "exact"` requires equal counts for all conditions. Iteration-specific units require `planned_iterations` to match the run's `n`. Use `ep jobs set-treatment-assignment jobs.ep --clear` to remove a schedule. This version accepts explicit schedules on the default Cartesian assignment plan; it rejects probability-based assignment, stratification, custom Jobs assignment plans, and Humanize.

Configure exact-count question sampling in a saved Survey package, then inspect and validate the policy:
```bash
ep surveys set-question-sampling survey.ep \
  --eligible-question q1 --eligible-question q2 --eligible-question q3 \
  --sample-size 2 --required-question q1
ep surveys show survey.ep
ep validate --file survey.ep
```
Declare and inspect question-order blocks:
```bash
ep surveys add-question-order-block survey.ep \
  --name attitudes \
  --question trust --question fairness --question satisfaction
ep surveys show survey.ep
ep validate --file survey.ep
```
Required questions count toward `--sample-size`; questions outside the eligible pool are always asked. Each respondent/scenario/iteration gets one sample shared across model variants. Results expose sampled and omitted questions under `randomization.*`.
Question-order blocks contain at least two contiguous, independent questions in declared order. Custom branching, internal piping or memory dependencies, and instructions inside a block are not supported. `questions_to_randomize` continues to randomize answer options. Humanize currently reports a capability error for surveys with question-order blocks or question sampling.

If validation fails, correct the reported problem before running the object.

## Preview saved objects in Markdown

```bash
ep inspect agents.ep --markdown --page 2 --page-size 5
ep inspect scenarios.ep --markdown
ep inspect models.ep --markdown
ep inspect job.ep --markdown --page-size 20
ep inspect results.ep --markdown --page 3 > results-page-3.md
```

`ep inspect --markdown` starts at page 1 with 10 entries per page. The header shows the
displayed range and total. It accepts the same packages, JSON files, or remote references
as `ep inspect`. Local Markdown previews use the saved package contents. Plain
`ep inspect` returns its JSON summary.

| Object | What one entry contains |
| --- | --- |
| AgentList | One agent with its name, stacked trait labels and values, custom instructions, and trait descriptions. |
| ScenarioList | One scenario. Short records share a table. Long or wide records use stacked fields. |
| ModelList | One model with its inference service and parameters. |
| Survey | One question with its original number and routing. Use `ep surveys show survey.ep --markdown --page 2 --page-size 5` to combine paging with the questionnaire display flags. |
| Jobs | One saved question, agent, scenario, or model, in that order. The header shows component counts. Inspecting does not run the job. |
| Results | One result with its answers, model, agent, scenario, and iteration. |
| Collection | One typed object reference. |
| Prompt or playbook | One line of saved prompt text. |

For example, `agents.to_markdown(page=2, page_size=5)` returns the second page in Python.
Use `ep inspect survey.ep --markdown` for the same quick, paged look you would give
any study object. Use `ep surveys show survey.ep --markdown` to read or export the
whole questionnaire, or to include question names, types, or all dropdown choices.

## Run with language models

For hosted execution, configure an Expected Parrot account and API key as described in [Managing Keys](/en/latest/api_keys). Check authentication and connectivity:

```bash
ep auth status
ep check
```

Discover available models:

```bash
ep models --text
```

Replace `MODEL_NAME` below with a model returned by the catalog. These commands build and estimate a job; the final command runs it and may incur model usage costs:

```bash
ep models create --model MODEL_NAME --output models.ep
ep jobs build --survey survey.ep --models models.ep --output jobs.ep
ep validate --file jobs.ep
ep jobs cost jobs.ep
ep run jobs.ep --output results.ep
```

Blocking runs require an output file. Use `.ep` for a Results package or `.json` for serialized data.

To disable remote inference, add `--local`. This runs execution on your machine but can still call a model provider over the network and incur charges. Provider credentials or a configured local model server are required for real model calls. See [Connect to your own model server](/en/latest/language_models#connect-to-your-own-model-server) for endpoint configuration.

When overriding a saved job, `--agent_list`, `--scenario_list`, and `--model_list` replace the corresponding component. `--model` replaces the model list with one model; it cannot be combined with `--model_list`.

## Submit a background job

Use background execution for long remote jobs:

```bash
ep run jobs.ep --background
```

The response includes job metadata under `data.meta.remote_job` when available. Read its `job_uuid` and use that value in follow-up commands. Replace `JOB_UUID` below with the returned identifier:

```bash
ep jobs status JOB_UUID
ep jobs results JOB_UUID --output results.ep
ep jobs errors JOB_UUID --output error.md
```

Fetch results after the job completes; fetch the error report when investigating failures. To submit, wait, and save in one command:

```bash
ep run jobs.ep --background --wait \
  --poll_interval 10 --timeout 3600 --output results.ep
```

`--background` alone returns before responses are ready. Do not combine `--background` with `--output` unless you also use `--wait`.

## Collect human responses

After configuring Expected Parrot authentication, you can publish the saved survey for human participants:

```bash
ep validate --file survey.ep
ep humanize create --survey survey.ep --name "Service feedback"
```

`humanize create` creates a hosted survey. Read the returned survey identifier and respondent URL from the JSON response. Share the respondent URL with participants when you are ready to collect responses.

Replace `HUMAN_SURVEY_UUID` with the returned identifier to inspect the survey and save responses:

```bash
ep humanize status HUMAN_SURVEY_UUID
ep humanize responses HUMAN_SURVEY_UUID --output human-results.ep
ep results columns --file human-results.ep
ep results select --file human-results.ep --column "answer.*" --limit 5
```

`humanize responses` saves completed responses. Add `--include-partial` to also save responses that are still being taken; `agent.response_status` tells them apart.

To stop taking new responses, pause the survey. Respondents who open the link are told it's closed, and anyone partway through can still finish. Resume it to accept new respondents again:

```bash
ep humanize pause HUMAN_SURVEY_UUID
ep humanize resume HUMAN_SURVEY_UUID
```

You can also publish from a Jobs package with `--jobs`. Jobs used for human surveys must not include models. If they contain scenarios, supply `--scenario_method`; use `ep humanize create --help` to see the available assignment methods.

See [Humanize](/en/latest/humanize) for survey configuration and [Prolific studies](/en/latest/prolific) for participant recruitment.

## Inspect and export saved responses

Use results commands on saved files:

```bash
ep results columns --file results.ep
ep results select --file results.ep \
  --column answer.feedback --column model.model --limit 5

ep results export results.ep \
  --column answer.feedback --output answers.csv
```

Repeat `--column` for multiple columns; do not pass a comma-separated list. Inspect available columns before selecting them. Use a bounded `select` to review responses and `export` to save larger datasets. Results queries support `.ep`, `.json`, and `.json.gz` files.

For randomized surveys, inspect assignment and exposure provenance as structured columns:

```bash
ep results columns --file results.ep
ep results select --file results.ep \
  --column randomization.assignment_id \
  --column randomization.option_orders \
  --column randomization.planned_question_order \
  --column randomization.exposure_order
ep results export results.ep \
  --column randomization.assignment_id \
  --column randomization.exposure_events \
  --output randomization.csv
```

## Automation conventions

- Discover commands and schemas from the installed version before generating inputs.
- Validate inputs, check every response's `status`, and read `warnings` before continuing.
- Keep credentials out of logs and shared files. Use the configuration described in [Managing Keys](/en/latest/api_keys).
- Use saved objects and returned identifiers to continue work. A background submission is not a completed run.
- Pass explicit pagination, for example `ep jobs list --page 1 --page_size 20`, and inspect returned pagination metadata.
- Retry remote operations only when doing so will not duplicate work. Check job status before submitting another run.
- Obtain explicit user direction before destructive actions such as `ep delete` or `ep jobs cancel`; both require `--yes`.

### Exit codes

| Exit code | Meaning |
| --- | --- |
| `0` | Success |
| `1` | General error |
| `2` | Usage error |
| `3` | Resource not found |
| `4` | Authentication error |
| `5` | Validation error |
| `6` | Remote service error |

Use the JSON error's `code`, `message`, and optional `suggestion` to decide the next step. For example, correct flags after `USAGE_ERROR`, inspect schemas after `VALIDATION_ERROR`, and check credentials after `AUTH_ERROR`.
