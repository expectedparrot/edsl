A `Model` selects the language model that will generate answers to your survey. Its **service** identifies where EDSL sends the requests; its **parameters** control supported generation settings, such as response length. An [Agent](/en/latest/agents) supplies a respondent profile, while the Model supplies the language model answering from that profile.

Use one Model to run a study or a ModelList to compare several model configurations on the same inputs. Select from the current catalog because model availability and supported settings change.

<span id="language-models" />

## Discover and select models

```python
from edsl import Model

Model.services()
Model.available()
```

`Model.services()` lists inference services; `Model.available()` lists models you can select. Run each expression in its own notebook cell to display both tables. Discovery may contact provider or Expected Parrot services. The [model catalog](https://www.expectedparrot.com/models) includes availability and pricing. See [Managing Keys](/en/latest/api_keys) for hosted and provider credentials.

`Model()` selects the configured default. Inspect `model.model` and `model.parameters` and save the configuration with your study. For a named selection, use `Model(model_name, service_name=provider)` with values you have verified in the catalog.

## Compare models on matched inputs

Construct a `ModelList` from your selected configurations and apply it with `job.by(models)`. Hold the questions, scenarios, and agent instructions constant so differences can be traced to model configuration. See [Model comparisons](/en/latest/guides/model_comparisons).

Do not assume settings such as temperature, token limits, or reasoning effort have the same meaning or valid values across providers. Unsupported values can fail at execution time even when a configuration serializes successfully.

## Reasoning and provider configuration

OpenAI adapters accept reasoning settings, with request formatting depending on the adapter. Explicit `reasoning_effort` is forwarded for provider validation; with the Responses adapter, an explicit effort overrides the effort inside a `reasoning` dictionary. Supported values depend on the selected model.

See [Provider configuration](/en/latest/guides/providers) for selecting services and inspecting parameters, and the [adapter source](https://github.com/expectedparrot/edsl/tree/main/edsl/inference_services) for implementation details. Record effective settings with results and check provider documentation before adopting a model-specific option.

## Persimmon interviews

Persimmon is a conversation model. For a standard question, EDSL sends the question as the opening turn and returns the simulated respondent's next turn as the answer. For `QuestionInterview`, Persimmon generates turns for both the interviewer and respondent; the EDSL `Agent` description supplies the respondent persona. Set `PERSIMMON_API_KEY` in the environment or in `.env`.

```python
from edsl import Agent, Model, QuestionFreeText, QuestionInterview, Survey

model = Model("persimmon-v0.1", service_name="persimmon")
respondent = Agent(
    traits={"life_stage": "busy parent", "shopping_habit": "uses grocery delivery occasionally"},
    instruction="Answer in character with specific everyday details.",
)

question = QuestionFreeText(
    question_name="grocery_habits",
    question_text="How do you usually decide whether to order groceries for delivery?",
)
results = Survey([question]).by(respondent).by(model).run()
results.select("answer.grocery_habits")
```

Use the same model and agent with an interview question when you want a longer exchange:

```python
from edsl import QuestionInterview, Survey

question = QuestionInterview(
    question_name="experience",
    question_text="Understand how people choose a grocery delivery service.",
    interview_guide="Ask about their most recent order, what went well, and what they would change.",
    max_turns=2,
)
results = Survey([question]).by(respondent).by(model).run()
results.select("answer.experience")
```

Each interview creates a Persimmon conversation and generates one interviewer turn followed by one respondent turn for each `max_turns` iteration. Each standard question creates a short conversation with one questioner turn and one respondent turn.

## Connect to your own model server

Use EDSL's `openai_compatible` service to connect to a server that exposes an OpenAI-compatible chat-completions endpoint. Start the server first, then replace `MODEL_NAME` with a model identifier it serves and `SERVER_BASE_URL` with its API base URL, including `/v1` if required by that server.

```python
from edsl import Model

model = Model(
    "MODEL_NAME",
    service_name="openai_compatible",
    base_url="SERVER_BASE_URL",
    # For an authenticated server, also set:
    # api_key_env="MY_MODEL_API_KEY",
)
```

If the server requires authentication, set an environment variable containing its key and pass that variable's name as `api_key_env`. EDSL saves the variable name with the model configuration, without including its secret value.

With a `survey` you have already constructed, run it through the configured endpoint:

```python
results = survey.by(model).run(
    disable_remote_inference=True,
    disable_remote_cache=True,
)
results.select("answer.*")
# In a script, append .print() to display the answers.
```

`disable_remote_inference=True` runs orchestration on your machine; requests go to the configured server, which may be local or remote. `disable_remote_cache=True` disables Expected Parrot's remote cache. The CLI equivalent for local orchestration is `--local`.

Supported model parameters and response formats depend on the server and model. Use the server's own documentation for installation and tuning—for example, the [llama.cpp server guide](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).

For an offline execution check, use the test model in the [Run your first survey](/en/latest/starter_tutorial) tutorial. Test responses demonstrate the data flow and do not measure model performance.

## Common methods

| Call | Arguments and result |
| --- | --- |
| `Model()` | Create a configuration for your default model. |
| `Model(model_name, service_name=provider, **parameters)` | Choose a model and provider, with provider-specific parameters. |
| `Model.available(search_term=None, service_name=None)` | Return a ModelList from the available catalog, optionally filtered by name or service. Discovery can contact remote services. |
| `Model.services()` | Return a ScenarioList describing registered inference services. |
| `ModelList([model, ...])` | Collect configurations for a comparison. |
| `model.model` / `model.parameters` | Inspect the selected name and parameter dictionary. |

You can practice configuring multiple models locally:

```python
from edsl import Model, ModelList

models = ModelList([
    Model("test", canned_response="Clear"),
    Model("test", canned_response="Unclear"),
])
models
# In a script: models.print()
```

These test models return fixed answers. Replace them with configurations from the catalog for a real model comparison, then pass the list to `job.by(models)`.

## Narrow the catalog and reuse selections

`Model.available(service_name=provider)` restricts discovery to a service; add `search_term` to filter names. `Model.search_models(search_term)` provides name search. To inspect only services for which you have configured provider keys, use `Model.services_with_local_keys()`; `Model.available_with_local_keys()` lists their models. These are discovery methods, not guarantees that a particular API call will succeed.

`Model.check_working_models(works_with_text=True, works_with_images=True)` retrieves Expected Parrot's working-model catalog with capability filters. It reads catalog information rather than running your survey. Use `output_format="scenario_list"` when you want catalog rows instead of model configurations.

For PDF, video, and audio inputs, choose a model that supports the specific media type; the image filter only describes image support. See [Files and media as scenarios](/en/latest/scenarios#data-and-files) for examples, including Google video and audio inputs.

A ModelList can be inspected with `to_scenario_list()` or `to_dataset()`, filtered with `filter(expression)`, and saved with `save("models.ep")` for later `ModelList.load("models.ep")`. `ModelList.from_names(names)` constructs configurations from a list of model names; use explicit `Model(name, service_name=provider)` objects when the provider needs to be unambiguous.

## Provider tools

Some inference services expose tools that run on the provider's infrastructure.
OpenAI Responses, xAI Responses, Anthropic Messages, Google Gemini, and Meta's Responses API
support provider-hosted tools through the same EDSL interface. Attach the
provider's tool declaration to a model, then use the model in a normal EDSL job:

```python
from edsl import Model, QuestionFreeText, Survey

model = Model("gpt-4.1-mini", service_name="openai_v2").with_tools(
    {"type": "web_search"}
)
survey = Survey(
    [
        QuestionFreeText(
            question_name="answer",
            question_text="What changed in the latest release of Python? Include sources.",
        )
    ]
)
results = survey.by(model).run(
    offload_execution=False,
    disable_remote_inference=True,
)
trace = results[0]["raw_model_response"]["answer_raw_model_response"]
```

The provider performs the search as part of its Responses API request. EDSL returns
the final text as the ordinary answer and preserves the provider response, including
search events and citations, in the question's `raw_model_response` fields (for example,
`answer_raw_model_response`). Provider tool declarations are serialized with the model
and included in cache identity.

Provider-hosted tools currently work through `service_name="openai_v2"`,
`service_name="xai_responses"`, `service_name="anthropic"`,
`service_name="google"`, and `service_name="meta"`.
Application function tools, where EDSL must execute a returned function call and
send its result back to the model, are a separate capability and are not supported
yet. Direct execution is required because remote EDSL workers do not yet support
tool requests. The provider must support the selected tool and model; unsupported
combinations return the provider's API error.

xAI exposes hosted Web Search, X Search, and Code Execution through its
Responses API. Use `service_name="xai_responses"` to select that API path; the
existing `service_name="xai"` continues to use xAI's Chat Completions API:

```python
xai_model = Model("grok-4.7", service_name="xai_responses").with_tools(
    {"type": "web_search"}
)
xai_results = survey.by(xai_model).run(
    offload_execution=False,
    disable_remote_inference=True,
)
xai_raw = xai_results[0]["raw_model_response"]["answer_raw_model_response"]
```

Use `{"type": "x_search"}` for posts on X or `{"type": "code_interpreter"}`
for provider-hosted Python execution. Tool invocation may incur provider charges
in addition to token costs.

The same interface accepts other Responses API tool definitions. Code Interpreter
needs an automatic container:

```python
code_model = Model("gpt-4.1-mini", service_name="openai_v2").with_tools(
    {"type": "code_interpreter", "container": {"type": "auto"}}
)
calculation = Survey(
    [
        QuestionFreeText(
            question_name="calculation",
            question_text="Use Python to compute the sum of squares from 1 through 20.",
        )
    ]
)
code_results = calculation.by(code_model).run(
    offload_execution=False,
    disable_remote_inference=True,
)
```

File Search requires a populated OpenAI vector store. Create the store and upload/index
files with the OpenAI Files and Vector Stores APIs, then supply its ID:

```python
file_model = Model("gpt-4.1-mini", service_name="openai_v2").with_tools(
    {
        "type": "file_search",
        "vector_store_ids": ["VECTOR_STORE_ID"],
        "max_num_results": 3,
    }
)
file_results = survey.by(file_model).run(
    offload_execution=False,
    disable_remote_inference=True,
)
```

Tool-specific request fields are passed through to OpenAI and validated there. EDSL
stores each complete provider response under the question's `raw_model_response`
fields, so tool event types, statuses, and returned citations can be inspected there.

Meta's Responses API also provides server-side web search. Use a Meta model with
`service_name="meta"` and the `web_search` tool declaration:

```python
meta_search_model = Model("muse-spark-1.3", service_name="meta").with_tools(
    {"type": "web_search"}
)
meta_results = survey.by(meta_search_model).run(
    offload_execution=False,
    disable_remote_inference=True,
)
```

Meta returns search calls and cited response messages in its Responses output.
EDSL keeps that complete output in `raw_model_response` and uses the final answer
message for the question answer, omitting intermediate commentary from the answer
field. Meta's `tool_search` can find developer-defined tools, but executing those
tools and continuing the conversation still requires application-side logic.
See Meta's [search grounding](https://dev.meta.ai/docs/search-grounding) and
[tool calling](https://dev.meta.ai/docs/tool-calling) documentation.

Anthropic Messages has its own versioned server-tool declarations. For example,
web search can be enabled with `web_search_20250305`:

```python
anthropic_search_model = Model("claude-haiku-5-5", service_name="anthropic").with_tools(
    {"type": "web_search_20250305", "name": "web_search", "max_uses": 2}
)
search_results = survey.by(anthropic_search_model).run(
    offload_execution=False,
    disable_remote_inference=True,
)
```

Anthropic's code execution tool can run a calculation in the provider's sandbox:

```python
anthropic_code_model = Model("claude-haiku-5-5", service_name="anthropic").with_tools(
    {"type": "code_execution_20250825", "name": "code_execution"}
)
code_results = calculation.by(anthropic_code_model).run(
    offload_execution=False,
    disable_remote_inference=True,
)
```

Web fetch can be restricted to specific domains. This example allows pages from
Anthropic's documentation site only:

```python
anthropic_fetch_model = Model("claude-haiku-5-5", service_name="anthropic").with_tools(
    {
        "type": "web_fetch_20250910",
        "name": "web_fetch",
        "max_uses": 1,
        "allowed_domains": ["platform.claude.com"],
    }
)
fetch_results = survey.by(anthropic_fetch_model).run(
    offload_execution=False,
    disable_remote_inference=True,
)
```

Anthropic returns server-tool activity and results as content blocks in the
provider response, which EDSL retains under `raw_model_response`. Server tools
execute within the Anthropic request; EDSL does not run a client-side tool loop.
Tool names and versions are provider-specific. See Anthropic's documentation for
[web search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool),
[code execution](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool),
and [web fetch](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool).

Google Gemini's `generate_content` API accepts tool declarations in its own
configuration format. For example, Google Search uses `google_search`:

```python
google_search_model = Model("gemini-2.5-flash", service_name="google").with_tools(
    {"google_search": {}}
)
google_search_results = survey.by(google_search_model).run(
    offload_execution=False,
    disable_remote_inference=True,
)
```

The same pattern enables sandboxed Python execution or URL context. Include the
URL in the question when using URL context:

```python
google_code_model = Model("gemini-2.5-flash", service_name="google").with_tools(
    {"code_execution": {}}
)
google_code_results = calculation.by(google_code_model).run(
    offload_execution=False,
    disable_remote_inference=True,
)

google_url_model = Model("gemini-2.5-flash", service_name="google").with_tools(
    {"url_context": {}}
)
page_question = QuestionFreeText(
    question_name="page_summary",
    question_text="Summarize the tool-use guidance at https://ai.google.dev/gemini-api/docs/url-context",
)
page_results = Survey([page_question]).by(google_url_model).run(
    offload_execution=False,
    disable_remote_inference=True,
)
```

Google's SDK represents these built-in tools with provider-specific fields rather
than a generic `type` field. EDSL passes those declarations to the Google Gen AI
SDK's `GenerateContentConfig`; the complete response, including grounding metadata
or code execution parts, remains available in `raw_model_response`. See Google's
[Search grounding](https://ai.google.dev/gemini-api/docs/google-search),
[code execution](https://ai.google.dev/gemini-api/docs/code-execution), and
[URL context](https://ai.google.dev/gemini-api/docs/url-context) guides for
provider and model availability details.

For Gemini models that support thinking, EDSL requests Google's optional thought
summaries by default. Returned summaries remain in `raw_model_response` and are
also exposed in `reasoning_summaries_dict` (for example,
`result["reasoning_summaries_dict"]["answer_reasoning_summary"]`). Disable them
with `Model("gemini-2.5-flash", service_name="google", include_thoughts=False)`.
These are provider-generated summaries, not a complete transcript of the model's
internal reasoning, and Google may omit them for a response. See Google's
[thinking documentation](https://ai.google.dev/gemini-api/docs/thinking).
